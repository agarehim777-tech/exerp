# Architecture rules

- Extract application orchestration into focused hooks and domain modules rather than relocating it into shared monoliths; this keeps changes independently testable.
- Stabilize refresh callbacks and scope asynchronous reads to their current tenant before publishing results; late responses must not restore another tenant's data.
- Retain one authoritative persistence writer per collection during incremental migration; dual writers can resurrect deleted records.
- Keep shared UI implementations in TypeScript and retain explicit-extension legacy re-export bridges only during migration; extensionless self-imports can resolve to the bridge itself.
- Keep delivery calculations in the warehouse domain module and shared business dates independent of appDomain; this avoids cyclic module initialization during extraction.
- Compose application screens from shared typed UI primitives and semantic layout classes; configurable badge colors belong in the shared badge rather than page-local style objects.
- Persist collection records through dedicated domain adapters with one writer; the retired generic collection table must never be a reload fallback.
- Keep typecheck in the release and CI gates; migration bridges must re-export explicit TypeScript extensions to avoid self-imports.
- Static presentation styles live as semantic classes in src/styles/static-styles.css; keep inline style only for runtime-computed values so theming stays centralized.
- Format fixed-decimal money only through services/format.js formatAmount and compute sellable stock only through shared/lib/stockMath.js; local copies drifted and showed different numbers.
- appDomain.jsx is a barrel over appDomain<Area>.jsx modules; add new domain logic to the area module, not the barrel, so areas stay independently editable.
- appDomainHr.jsx is only a re-export bridge: HR logic lives in shared/lib/hrDomain.ts and HR components in modules/hr/components/HrPlatforms.tsx and HrStructure.tsx. Add or change HR code there, never in appDomainHr.jsx.
- appDomainWarehouse.jsx is only a re-export bridge: warehouse stock logic lives in shared/lib/warehouseDomain.ts and warehouse components in modules/warehouse/components/WarehouseBalances.tsx and WarehousePanels.tsx. Add or change that code there, never in appDomainWarehouse.jsx.
- SalesOrderModals.jsx is only a re-export bridge (AppWidgets.jsx lazy-imports it): the modals live in modules/sales/components/SalesOperationModal.jsx and SalesOrderModal.jsx; their pure form helpers (seller bonus cap, customer identity, search options, buildSalesProductOptions) live in modules/sales/services/salesOrderForm.ts and the combobox in components/SearchableOrderSelect.tsx. Change those there; reuse shared/lib/serialStockHelpers.ts for serial lookups instead of local copies.
- appDomainSales.jsx keeps only the sales/CRM UI components (WorkflowSteps, CustomerCreditHistory, Customer360Modal) and re-exports the sales domain logic, which lives in shared/lib/salesDomain.ts (seller bonuses, sales order filters/search/risk, Customer 360 summary, CRM pipeline rows and filters, customer/credit/order/contract lookups). Change that logic in salesDomain.ts; TypeScript modules import it from there.
- CreditsPage.jsx renders StartCreditModal and QuickCollectModal from modules/credits/components/CreditActionModals.jsx (it re-exports StartCreditModal for old imports); change the start-credit and quick-collect flows there.
- appDomainFinance.jsx keeps only InvoicePrintModal and re-exports the rest: the credit detail UI (detail modal, contract snapshot, schedule, payment form, health summary) lives in modules/credits/components/CreditDetail.tsx, and the finance domain logic, which lives in shared/lib/financeDomain.ts (month-close checklist, support ticket context, receivable/invoice aging, daily cash summary, expense statuses and cash posting, finance ledger and scenario). Add or change that logic in financeDomain.ts; TypeScript modules import it from there, not from the .jsx file.
- SalesInvoicesPage.jsx renders the billing run from modules/finance/components/BillingRunPanel.jsx (unbilled orders/projects and the editable invoice preview); change that flow there, not in the page.
- shared/state/moduleActions.js composes the module page commands from per-area factories (finance: shared/state/financeModuleActions.ts for e-invoice, journal export, tax payment task and receivable sync; the action timestamp lives in shared/state/actionStamp.ts). Add or change an area's commands in its factory and keep createModuleActions' returned names stable for App.jsx.
- ProcurementPage.jsx computes its derived data (PO metrics, invoice totals, payments per PO, list filters, dashboard stats) through modules/procurement/procurementSelectors.ts inside useMemo; change those calculations in the selectors and keep the useMemo dependency arrays in the page. Its registry reads (vendors, products, POs and lines, receipts, vendor invoices, legacy PO payments) and loading state live in modules/procurement/useProcurementRegistry.ts; add or change procurement reads there, paged with readAllRows and guarded by isCurrent(). Procurement actions move into one hook per area (vendors: modules/procurement/useVendorActions.ts, RFQs: useRfqActions.ts, purchase orders: usePoActions.ts, PO payments: usePoPaymentActions.ts, goods receipts (GRN): useReceiptActions.ts, vendor invoices and 3-way match: useInvoiceActions.ts, vendor invoice payment: useInvoicePayment.ts (its resetInvoicePayment is stable and runs in the page load effect); the PO form state stays in the page because RFQ conversion fills it too); each hook takes the page's shared setters (setError, setNotice, setSaving, setTab, load) as parameters.
- appHelpers.jsx has been split into typed modules, one area per PR, and is now only a re-export bridge (notifications: notificationHelpers.ts, receivables: receivableHelpers.ts, messaging: messagingHelpers.ts, serials/stock rows: serialStockHelpers.ts, permissions: permissionHelpers.ts, invoices/accounting/tax: financeHelpers.ts, KPI targets: kpiHelpers.ts, API webhooks/secrets: apiIntegrationHelpers.ts, credit records/risk/aging: creditRecordHelpers.ts, project ROI: projectHelpers.ts, production plans: productionHelpers.ts, onboarding/help: onboardingHelpers.ts, seller bonus/order lines/sales credit: salesOrderHelpers.ts, delivery/finance list filters: listFilterHelpers.ts, numbering/state hydration: stateHydration.ts, dashboard actions/insights: dashboardHelpers.ts, report rows/package: reportHelpers.ts, readiness reports: readinessHelpers.ts, payroll expense: payrollExpenseHelpers.ts); it re-exports moved functions so old imports keep working. Add or change logic in the area module, never re-add a moved function to appHelpers.jsx.
- Tenant-wide reads must page with readAllRows, never .limit(N); PostgREST silently caps at 1000 rows.
- Report totals, trend, risk register and module analytics come from report_* database functions; full rows load only for a warehouse filter or an export, so client sums are just the fallback.
- Database schema changes (tables, columns, functions, policies, grants) go into a new supabase/migrations/<YYYYMMDDHHMMSS>_<name>.sql file; it is the source of truth for local E2E, the PGlite tests and production deploys. A file in drizzle/migrations reaches none of them: whenever you add one, also port its SQL into supabase/migrations and add its entry to drizzle/migrations/PORTED.json, or CI fails.
- JavaScript files are type-checked by npm run typecheck:js (checkJs, non-strict) against scripts/checkjs-baseline.json: never add new errors to a .js/.jsx file; after fixing errors or converting a file to TypeScript, run npm run typecheck:js -- --update so the baseline only goes down.
- Page-level URL state goes through shared/hooks/usePageQuery.jsx; its updates resolve against the history's current URL, not the last rendered router location (BrowserRouter commits navigation in a transition). Never call useSearchParams' setter or a relative "?..." navigate for page state: typing right after a sidebar click would pull the user back to the previous module.
